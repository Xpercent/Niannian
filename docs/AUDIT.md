# 重构前验证与架构决策

> 历史资料：本文是对只读参考工程 project4 的历史审查，不是当前 project5 的需求或缺陷清单；本地失败兜底等旧行为已变更，当前实现见 HANDOFF.md 与 ARCHITECTURE.md。

日期：2026-10-09（Asia/Shanghai）。参考工程 project4 只读，开发目录 project5。

## 微信先接入

在编写新应用代码之前，使用 project5 的 64 位 Python 3.13 与现有上游 WeChatDB 接入正在登录的微信 4.x。枚举到 81 个真实会话，读取 569 条真实消息。本地读取证据保存在 data/raw-wechat.json；不提交聊天内容、账号标识和解密缓存。没有人工编造消息，也没有发送测试消息。

初次通过原版归一化的 172 条消息本人计数为 0。进一步核对原始 569 条，sender_id=2 或 sender_username=账号 的 23 条疑似本人消息均与权威群前缀或 XML 根发送者冲突，不能将文档中的 sender_id=2 直接当成真实本人。实际确认权威发送者=账号的 12 条（群消息 1、私聊 XML 11）；由同会话明确原文证据确认非 2 的 numeric self ID。新版适配器按原文身份、同会话已验证数字映射的顺序判断，冲突留痕；身份不明确时禁止自动完成待办。此更正优先于上游文档假设。

## 原版运行与测试

执行 project4/.venv/Scripts/python.exe -m unittest discover -s tests -v：136 项，135 通过，1 失败。失败项 test_node_pure_function_suite_passes：Node 子进程返回码为 0 但标准输出为空，断言找不到 fail 0。该结果不等同于原前端验证通过。原版 API TestClient 已执行真实 ASGI 应用生命周期与 HTTP 接口，其测试混合合成消息，不将那些数据带入新版。

## 需要保留的业务能力

- 双向消息、账号身份、原始时间与本机附件；来源幂等、先持久化再提炼。
- 合并窗口与静默窗口独立；暂停只停止提炼，不丢失采集消息。
- 云端严格结构化输出与本地保守回退；本人承诺不创建任务、他人完成不核销本人任务。
- CREATE / UPDATE / RESOLVE / IGNORE、任务原文与变更审计、取消与恢复。
- 规则、画像、可持久化设置、进度与取消、导出和一致性备份。

## 技术债与处理

| 原版问题 | 新版决策 |
| --- | --- |
| 导入 API 模块就打开数据库、播种演示数据、创建全局服务 | 应用工厂和显式容器，生命周期负责启停，无演示数据或手动消息入口 |
| HTTP 桥接、outbox、上游监听线程与全局进程清扫并存 | 一个受控串行读取 worker，直接写本机仓储；消息与采集 checkpoint 同事务；独立缓存，不杀其他项目进程 |
| 本人标识不完整 | 上游明确本人 ID 和 username 两条身份路径校验，保留 sender_key |
| 固定行动词在云端前永久过滤 | 无明确忽略证据的文本交给模型；本地规则仅作为可解释的降级 |
| 同一段只能生成一个待办 | 一段支持多个严格校验指令 |
| 先问完全部批次再落库，本轮 pending 快照失效 | 会话内有序批次，批内引用新任务需要明确引用标识 |
| 大量 julianday 排序无法利用原始时间索引 | 摄入统一 UTC 定长时间，索引覆盖会话时间和队列 |
| 设置/轮次/全局引擎状态混杂 | 文件配置快照、作业协调器、业务引擎、仓储职责分离 |
| 前端多层补丁、样式重复、交互入口拥挤 | 全新亮色工作台、任务中心、来源侧栏，独立消息/规则/画像/设置视图 |

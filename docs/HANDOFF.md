## 当前提炼链路

1. 一个串行微信线程只读采集真实消息，消息与 checkpoint 同事务提交，源键按账号/会话隔离去重。
2. 一轮开始时冻结关注会话的未处理消息。自动轮次选择已满足静默条件的会话，按最早积压顺序依次处理；没有单轮/单会话消息数量上限。
3. 同账号、同会话、同发送者的相邻消息按拼接间隔合成段，保留全部真实源ID。同一会话所有批次连续处理，不轮转到其他会话。
4. 单次请求只按正文预算分批，没有段数上限。分批大小按每段原文字数与压缩目标的较小值估算，不含历史、已有待办、画像和模型指令；首段可超预算，因此不是总请求长度硬上限。
5. 超长段先完整交给已配置模型做普通总结压缩，不做行动摘要。提炼正文使用总结，原文用于来源与业务校验；摘要缓存存在来源末条的 `metadata_json.text_compression`，按原文、源ID、账号/会话、预算、模型/接口及提示词版本校验复用。
6. 每批发送前复查关注、账号与静默；压缩后再次检查。期间有新消息导致不满足静默时，跳过该会话本轮剩余消息，保留未处理标记，不在本轮等它重新静默。新到消息留到下轮。手动提炼跳过静默等待，仍校验关注和账号。
7. 模型已启用时，云端失败、无效/漏答或失效同批引用不交本地兜底；对应消息保持未处理，下轮再请求。同批有效结果独立落库。模型停用/未配置时保留本地规则处理；请求前过滤与统一 `guard_decisions` 始终保留。合法模型结果被业务校验拒绝，不等于请求失败。
8. 一段指令、任务来源/事件与消息 processed 同事务提交；取消保留未处理消息，人工编辑版本冲突不能通过重新读取版本绕过。
9. 整轮完成、取消或失败后才开始等待下一次自动间隔；手动轮次结束也重新计时。仍只有一个提炼作业通道。
10. 每次模型请求（压缩、单段、批量）另外写入 `model_calls` 诊断表，按 run_id 与会话、来源消息ID归属，含完整请求体、原样回复、finish_reason、usage、耗时、错误与校验前后对照。它是只读旁路：不参与事务、不改变 processed 与任务结果，写入失败只记日志；只保留最近 1200 次。

上述前端替换、预算开放、取消总量/段数/画像长度限制、总结压缩及失败留存均由用户在2026-10-10明确要求。它们替代旧约定；不能据此扩大到清库、全量重提炼、改关注或画像、发送微信、换模型等行为。

界面分模型服务、常用设置、默认折叠的高级设置、微信与数据。参数值以当前 API 为准，下表只是源码默认值。预算允许用户在配置范围内调节，默认值不是强制性能边界。

| 设置 | 默认 | 含义 |
| --- | --- | --- |
| 自动提炼间隔 | 300秒 | 整轮结束后开始等待 |
| 等待补充消息 | 60秒 | 自动发送前检查会话静默 |
| 连续消息拼接间隔 | 60秒 | 同发送者相邻消息拼接 |
| 每批正文预算 | 4200字 | 分批估算，不是整个请求硬上限 |
| 长消息压缩目标 | 2600字 | 超过时先总结，成功摘要不超此长度 |
| 历史参考 | 最多6条、1200字 | 同会话旧消息按完整正文选入，放不下整条省略；不复用摘要替代历史 |
| 已有待办参考 | 1600字 | 相关未完成任务编号、标题、优先级、期限 |
| 个人背景 | 完整画像 | 没有长度限制；空画像不猜身份 |
| 模型等待 | 40秒 | 单次网络请求 timeout |
| 回答变化程度 | 0 | temperature；不保证判断完全一致 |
| 提炼输出长度 | 单段700、多段1200 token | 输出上限，不是输入字数 |
| 微信扫描间隔 | 2秒 | 读取新消息，与提炼间隔不同 |
| 首次历史导入 | 100条 | 选择会话后的初次回读量 |
| 无需行动记录保留量 | 每会话100项 | 限制判定记录，不删除原始消息 |

`round_limit`、`per_session_limit`、`batch_limit`、`profile_chars` 已移除。旧配置文件中的这些字段读取时忽略，不主动改写本机文件。设置读取不回显密钥，接口地址仍可用于编辑；`/api/metrics` 不返回密钥或接口地址。API Key 保持本地明文，不写入文档、截图或提交。所有模型请求含 probe 和压缩均固定 `enable_thinking=false`。

## 数据保护与已知限制

- `config.json`、`data/`、`artifacts/`、`.venv/` 和微信缓存/附件都是本机资产，忽略文件不等于可删除。历史旧库/备份若仍存在也不得擅自清理；曾经改名或清理的授权不是持续清库授权。
- 禁止运行 `artifacts/reextract.py`、`artifacts/replay-final.py` 或复用其中重置/删除SQL。无针对性授权不重提炼历史、不删任务/事件/水位、不改本人映射、画像或关注。
- 运行库用 `Database.backup()` 或 `/api/backup` 一致性备份。恢复须停止本工程服务、保留当前快照并验证，不普通复制运行中的 `.db`。
- 本人身份必须有原文/XML根发送者或已验证映射依据；本人消息不CREATE/UPDATE，自动完成须本人且身份可信。跨会话引用、无来源任务和泛词关联禁止。
- 云端失败留存没有额外并发重试通道，持续失败可持续留在队列。群一直不静默可能延后提炼；一个大积压会话会延后后续会话。用户尚未要求改变这两项。
- 压缩提示词要求保留条件、例外、否定与更正，缺上下文标明未知；模型自报 complete 不是语义准确保证。压缩失败/输出截断/超预算保留消息。现有真实捕获最长958字，几千字通知的真实云端压缩质量尚未验证。
- 不做OCR、语音转写、自动下载媒体、微信发送、多用户服务或公网发布。模型判断仍可能遗漏或误解，需回查原文。
- schema 现为 v2：v2 只新增 `model_calls` 表与索引，走 `storage.MIGRATIONS` 顺序迁移并在 `Database.init()` 时登记 `schema_version`；本机正式库已于 2026-10-12 重启时自动迁移，迁移前用 `Database.backup('pre-diagnostics')` 留下一致性快照，迁移后 `PRAGMA quick_check` 为 ok。以后结构变化同样必须提供顺序迁移与旧库验证，不以删库重建替代。诊断表按 `MODEL_CALL_KEEP`（当前 1200 次）自动裁剪最旧行，只删诊断记录，不删消息、任务、事件、去重键或水位。历史提交改写前哈希不能用于当前操作；旧历史标签 `history-before-i18n` 只作恢复参照，不擅自切换或删标签。

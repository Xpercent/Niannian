# 重构记录

本文件按阶段记录 Niannian → Niannian2 重构的边界、决策与验证。
原项目 `Niannian/docs` 仅作架构理解材料，未经用户确认不作为约束。

## 阶段一：微信会话看板 + 只读接入（2026-10-14）

### 目标（用户定义）

搭好前端网页看板并接入微信，仅保留“微信会话”一页：能添加关注对话、
查看关注对话消息；与该阶段无关的功能按钮一律不做；非纯文本消息暂不格式化；
UI 与原版基本一致。

### 已确认的决策

1. 视觉参照 = 原版微信会话页（用户原话附图未送达，用户确认以原版为准）。
2. 关注会话后**自动导入**最近 N 条（默认 100），保留原版“历史上限+导入”
   按钮之外的最小闭环；不做手动导入按钮。
3. `.venv` 中指向失效旧路径的 `niannian 1.0.0` editable 残留已卸载。
4. `wechatauto-replica` 注册为 git submodule，锁定 1.2.5.1（fbfb026），
   与原项目一致；转换前逐文件哈希校验新旧副本一致。
5. 端口沿用 8765。

### 与原版的关键差异（本阶段有意为之）

- 关注语义收敛：原版“关闭监控仍继续采集”（因监控挂钩提炼调度）；阶段一
  没有提炼，故**取消关注即停止采集**，水位保留、重新关注续传不重复。
- 未搬运：媒体挂载/附件解析、身份映射与确认字段、实例锁、runs/model_calls
  诊断表、提炼/待办/画像/规则/设置/诊断各页。
- 前端组件全部本地手写（Button/Card/Input/Badge/Dialog），未引入
  shadcn/radix/clsx/tailwind-merge；配色沿用原版设计 token。
- 后端为全新最小实现：三张表（sessions/messages/checkpoints），
  借鉴原版“单线程串行读取 + 命令队列 + 水位同事务”的设计思路。

### 验证记录

- pytest：11 项通过（目录 upsert 保留关注态、去重、水位不回退、分页游标、
  发送者前缀/XML 根解析、is_self、去重键稳定性、无微信时明确报错）。
- 真机只读验证（本机登录微信）：连接成功，目录 89 个会话；关注群
  “26软工舍友の后花园”后自动导入 100 条真实消息；页面可见发送者昵称、
  时间、文本与 XML 原文（图片/转账/拍一拍未格式化，符合本阶段约定）；
  “加载更早消息”翻页正常；强制终止进程后重启，消息数与去重键保持
  100/100，水位续传未重复导入。
- UI 在内置浏览器实测：布局、状态条、弹窗关注流与原版一致度良好。

### 已知边界

- 消息正文长 XML 会占满气泡，属“暂不格式化”的约定表现。
- `catalog()` 在采集线程存活时同步读上游，超时 90s；线程未运行时回退本地目录。

## 修复：微信发送者名字解析错误（2026-10-14）

### 症状

群聊出现根本不是群成员的署名（“吴寒”16 条、“助班学长”1 条），私聊里自己发的
消息全部署上对方名字（王五月会话 100 条只有 5 条 `is_self=1`）。原版没这个表现。

### 根因

微信 4.x 消息分片库中 `Msg_*.real_sender_id` 是**该分片库自身 `Name2Id` 表的
rowid**，id 空间按分片各自编号；上游 `wechatauto.db._sender_id_index()` 却用
`message_resource.db` 的全局 `SenderName2Id` 去解析（全库没有任何一处用到正确的
分片 `Name2Id`），于是 `get_messages` 给出的 `sender_username` 是**另一个人的
wxid**——实测本群 `real_sender_id=5` 分片内是“我自己”，全局表解析成“吴寒”。

正文带 `wxid_x:` 前缀的行（群聊普通文本）被 `split_sender` 的前缀救回，所以看着
是对的；**没有前缀的行全部落到错误映射**：自己发的文本、emoji、图片、系统消息。
私聊完全没有群前缀，故 `is_self` 恒为 0、自己的话全成对方说的。

原项目有同一处缺陷（同版本子模块、同样的 `origin or sender_username` 优先级），
只是它只导入过“全员带前缀”的通知群（180 条 `is_self` 全为 0），症状未暴露。

### 改动

只在 `niannian/wechat.py`，**不动子模块**（子模块是 detached HEAD 的第三方锁定）：

> 后续：1、2 两条已在 2026-10-14 删掉——上游 1.2.6.1（issue #34）自己按分片解析了，
> 见文末「子模块升级到 1.2.6.1」。第 3 条（分片解析优先、正文前缀兜底）仍然有效。

1. 新增 `sender_alias_map(conn, table, wanted)`：在指定分片内按
   `(sort_seq, local_id)` 联合 `Name2Id` 还原真实发送者 wxid。
2. `IsolatedDB` 新增 `_fix_senders()`，并覆写 `get_messages` / `get_new_messages`
   套用之；分片解析不到的行把 `sender_username` 置空，避免沿用上游错值。
3. `normalize_message` 的发送者优先级由「正文前缀优先」改为
   「**分片解析优先、正文前缀兜底**」。

### 验证

- pytest 14 项通过（新增 3 项：分片 id 空间隔离、系统消息空名、自身 rowid 不被
  全局表串号 + 前缀与分片冲突时以分片为准）。
- 真机清库重采：群 100 条署名全部落在该群 4 名真实成员内，原 16 条“吴寒”→“我”；
  私聊 `is_self` 由 95/5 变为分布自然的 56/44；89 条带前缀的行前缀与分片解析零冲突。
- 增量轮询走同一 `_fix_senders`，单独取 `get_new_messages` 逐条断言发送者是群成员。
- 浏览器实测群聊与私聊署名、气泡归属均正确。

### 残留

拍一拍 appmsg 的 `real_sender_id=9` 在 `Name2Id` 中 `user_name` 为空，回落显示
“群成员”（原版同场景错显示为“助班学长”）；空名系统类消息的署名策略待用户定。


## 阶段二：图片显示（2026-10-14）

### 目标（用户定义）

让图片能显示出来；库里**只落图片本地链接**；清库重新采集。用户另外指出：
原版对"没在微信里手动点开过的图片"处理有问题——那些其实有预览图文件、
能被解析出来，但原版没做。

### 实测到的三条事实

1. **磁盘文件名哈希只在 `packed_info_data` 里**。正文 XML 的 `md5` 属性是另一套
   值：实测 `md5="6793b97e…"` 那条图，磁盘文件叫
   `3d11d910dfa03787d8b96a2964079fd2_t.dat`。按 XML 的 md5 去 attach 目录找，
   23 条一条都找不到。
2. **未点开过的图片只有 `_t.dat` 预览图，且能解出来**（单字节 XOR，从文件尾
   `FF D9` 反推密钥，不需要图片 AES 密钥）。实测两个会话 23 张图：
   原图 9 / 本机下发那份 6 / **只有预览图 8**。上游 `download_image(tier='best')`
   本来就会回落到预览图档，所以"能不能解"不是问题，问题在**什么时候去解**。
3. 原版把提取只挂在采集那一刻（`MediaCache.enrich` 在 `_store` 里调用一次），
   而微信的预览图是**翻到那条记录才落盘**的。它自己的库里就有证据：
   `45948752706@chatroom` 28 条图片只有 8 条留下 `local_file`，而今天对这 32 条
   重跑 `tier='best'` 是 **32/32 全部可解**——文件一直在盘上、能解析，库里却没链接。

### 改动

新增 `niannian/media.py`（全新实现，未搬运原版 `media.py`）：

- `hash_from_blob` / `media_hash_map`：按 `(sort_seq, local_id)` 从
  `packed_info_data` 批量取本机文件哈希（上游 `get_messages` 不返回该列）。
- `parse_image` / `summarize`：识别 `<img>` 附件，入库正文换成 `[图片]`
  （尺寸留在 metadata，不进摘要——`cdnthumb*` 是预览图尺寸，标出来会误导）。
- `pick_tier`：原图 > 本机下发 > 预览图；`_h.dat` 小于 1KB 视为下载中断空壳。
- `ImageStore.attach`：解密落到 `data/wechat/media/<账号指纹>/`，
  文件名 `<会话>_<sort_seq>[_档位].<ext>`，只回传相对链接。
- `safe_media_path`：链接最多两段、拒绝对称路径/盘符/UNC/`..`。
- `wechat.py`：抽出 `_each_shard` 共用分片遍历；`_attach_media` 在采集线程内
  补 `media_md5` + `local_file`；`IsolatedDB.media_hashes` 走同一条只读通道。
- `api.py`：`GET /media/{name}` 托管本机图片；`_link_media` 在**读取时**凭
  `media_md5` 再补一次链接并回写库——只碰文件系统与工程缓存，不需要采集线程。
- `web/`：`mediaUrl()` 拼链接；`message.tsx` 渲染缩略图 + 点击放大 Dialog，
  弹窗标注档位（原图/本机图/预览图）；无文件时显示"本机暂无该图片文件"。

### 验证

- pytest 22 项通过（新增 8 项：图片 XML 识别与拒绝、`packed_info` 哈希提取、
  档位优先级与空壳降级、`safe_media_path` 八种越界、`ImageStore.attach` 落盘
  位置与链接形状、账号目录指纹）。
- `tsc -b` 无错、`npm run build` 通过。
- 真机清库重采：200 条消息、23 条图片**全部**拿到本机链接（原图 9/本机图 6/
  预览图 8）；`GET /media/<预览图>` 返回 200 `image/jpeg`（`FF D8 FF`，118x210），
  原图返回 200 `image/png`。
- 越界探测 `../niannian.db`、`%2e%2e%2fconfig.json`、`C:/Windows/win.ini`、
  `/etc/passwd`、三段穿越路径全部 404。
- 回填路径实测：抹掉一条的 `local_file` 后再请求该页，链接自动补回并持久化。
- 浏览器实测：群会话 9 个图片气泡 8 个渲染出图，抹掉哈希的那条正确显示
  "本机暂无该图片文件"空态；放大弹窗 Esc 与遮罩点击均能关闭，档位标注正确。
  （内置浏览器标签处于 hidden 状态时 Chrome 不加载 `loading="lazy"` 图片，
  验证时改为 eager 后 9/9 全部加载；截图能力受限于该隐藏面，未取到视觉截图。）

### 已知边界

- 只处理图片；视频/语音/文件/卡片/拍一拍仍入库原始 XML。
- 预览图是低分辨率档，放大后仍模糊——已在弹窗标注"预览图"，不假装是原图。
  要真原图必须让微信去下载，那属于驱动界面，超出只读边界。
- 回填只认采集时已写入的 `media_md5`；早于本版本入库、没有该字段的老行不会补
  （本轮已清库重采，当前库内不存在这种行）。

### 阶段二补丁：图片档位标注与放大弹窗尺寸（2026-10-14）

用户实机反馈三件事，根因两个：

1. **横向图片的放大弹窗太小**。`cn()` 是纯字符串拼接，`Dialog` 基类写死了
   `max-w-lg`，调用方再传 `max-w-3xl` 会让两个宽度类同时挂在元素上，谁生效
   取决于样式表顺序——实测基类赢了，弹窗被钉在 512px，横图被 `max-h` 夹住后
   左右全是空白，所以"横图小、竖图正常"。改为基类**不再写死宽度与内边距**，
   由 `width` / `padded` 两个 prop 整档给出。
2. **预览图和正常图放大到一样大，糊得看不清**。弹窗里的 `<img>` 带了 `w-full`，
   等于把 118x210 的预览图强行拉到弹窗满宽。去掉 `w-full`，图片只用
   `max-w-full` + `max-h-[74vh]` 夹住、`w-auto` 保持原始尺寸，弹窗 `w-fit`
   收到图片实际大小——大图照样撑到 `min(1200px,94vw)`，小图不再插值放大。
3. **预览图要在气泡上就标出来**：缩略图左上角加"预览图"角标，只在
   `tier === 'thumb'` 时出现（原图/本机图不打标，避免给每张图都加噪音）；
   放大弹窗底部仍显示完整档位文案。

验证（内置浏览器量几何，视口 715x778）：9 个图片气泡中角标只出现在 5 个预览图
上；横向 1920x1080 的图弹窗 668x410、图片 666x375，无放大、无裁切；预览图
118x210 弹窗收紧到 141x245、按原始尺寸显示；`关注会话` 弹窗仍是 512x626 +
p-6 + Esc 可关，基类改动无回归。`tsc -b` 与 `npm run build` 通过。

## 阶段二补丁：群名片一档与系统消息署名（2026-10-14）

### 起因

用户问「群内昵称能不能获取到」。答案是能，而且拿到之后发现现有显示规则
**少了一档**。

### 实测结论

- 群名片**没有独立表列**（`chatroom_member` 只有 room_id + member_id），它藏在
  `chat_room.ext_buffer` 的 protobuf 里：字段 1=成员 wxid、2=群名片、4=邀请人。
  上游 `get_group_members()` 只读 contact 的昵称/备注，从没解析过这个 buffer。
  实测 `45948752706@chatroom` 32 名成员有群名片，宿舍群 `50333318698@chatroom`
  0 人设置过。
- 微信自己的优先级是 **备注 > 群名片 > 昵称**。依据不是猜的：
  `session.db.SessionTable.last_sender_display_name` 是微信算好的显示名，
  拿它和三方逐一比对，7 例「群名片/备注/昵称互不相同」的样本里
  6 例（无备注）跟随群名片、1 例（有备注，`助班学长` vs 群名片
  `厦门黄宸溢（26软2助班）`）跟随备注。
- 原逻辑（沿用原版）是 `备注 > 昵称`，**中间那档被跳过**。原项目带着同一个错，
  证据在它自己库里：`workspace.db` 存着 `sender_name='五大天王-陈德华'`
  （全局昵称），而微信在该群显示的是 `科技委员21陈永源`（群名片）。

### 改动

- 新增 `niannian/contacts.py`：`protobuf_fields`（只支持 wire 0/2，遇到别的类型
  就停，不猜偏移量把后面的数据当字段读）、`group_nicknames`、`display_name`。
- `IsolatedDB.room_nicknames()` 读 `chat_room.ext_buffer`；
  `IsolatedDB.display_names(user)` 按会话现算「备注 > 群名片 > 昵称」，
  `_store` 改用它替代全局 `nickname_map()`。
- **无发送者的行**（`Name2Id.user_name` 为空：拍一拍、撤回、进群提示）
  署名 `系统消息`、`sender_key` 置空不参与按人归组；原来会回退成
  `群成员`（更早是错标成某个群外成员）。
- 顺带修掉一个刚暴露的问题：群自己发的系统行正文前缀是**群 ID**
  （`45948752706@chatroom:`）而不是 `wxid_`，`split_sender` 的正则不认它，
  导致入库正文带着这串裸群 ID。现在剥掉但不认作发送者。

### 验证

- pytest 30 项通过（新增 8 项：protobuf 嵌套与 varint、群名片映射与"没设过"
  的成员、str/blob 两种 BLOB 形态、非成员与截断 buffer、三档优先级、
  系统消息署名、按会话显示名、群 ID 前缀剥离）。
- 真机清库重采 3 个会话共 300 条：通知群署名变成
  `学委陈晔显 / 科技委员21陈永源 / 文体委员吴彦朋 / 宣传委员46彭怡珍`；
  宿舍群不变（无人设群名片，`26同`/`影`/`(=°Д°=)`/`我` 保持）；
  私聊 `王五月 53 / 我 44 / 系统消息 3`。
- 逐条比对：把库里每个 `(会话, sender_key) → sender_name` 与
  `IsolatedDB.display_names()` 现算值对，**不一致 0 条**。
- 裸群 ID 前缀残留 0 条；39 张图片链接正常。
- 浏览器实测通知群 40 个气泡，署名全部是群名片。

## 阶段二补丁：读路径按时间排序 + 每会话独立的重新导入（2026-10-14）

### 起因与范围决定

用户要"导入更早历史"的入口。先出方案时我把它做成了完整链路（上游 keyset
翻页 + 新命令 + 新字段 + 到底判断 + 防连点），用户明确否掉：**该功能非刚需，
不要把系统搞复杂**。最终只做两件便宜的事，明确不做无限往回翻页。

### 关键发现：真正的工作量不在"取更旧的消息"

现有 `messages_page` 按**自增 id 倒序**翻页，游标是 `before_id`。它能成立纯粹
是因为消息永远"新的后入库"，id 顺序刚好等于时间顺序——这是巧合不是设计。

一旦重新导入，更旧的消息会带着**更大**的 id 插进来，按 id 排顺序就翻了。
所以"改排序"是必须先还的债，而不是可选优化。

### 改动

**A 读路径按时间排序**
- `messages_page` 排序键换成 `(sort_seq DESC, id DESC)`，游标换成
  `(before_seq, before_id)` 复合；索引 `(session_id, id)` → `(session_id, sort_seq, id)`。
- 同一 `sort_seq` 并列时用 id 做稳定 tiebreak：跨分片 `local_id` 本身会重复，
  没有更可靠的列能破并列，**接受同秒内按入库先后**（已写成测试固定行为）。
- 旧库若保留，索引定义不会自动换（`CREATE INDEX IF NOT EXISTS`），但排序是
  显式写在 ORDER BY 里的，**只影响性能不影响正确性**。本轮按惯例清库重采。
- API `before_seq`/`before_id` 两个参数；前端翻页游标同步。

**B 每会话独立的重新导入**
- `sessions.history_limit` 新列，**0 表示跟随全局默认**。刻意与全局
  `history_limit` 分开：调某一个会话不该影响其它会话（用户明确要求）。
- `Collector.reimport` 走已有命令队列进采集线程（只有它碰上游库），
  `_reimport` = 记下条数 → 清水位 → 复用现成的 `_import_recent`。
  **不删任何已入库消息**，重复行由 `source_id` 唯一键跳过。
- `POST /api/sessions/{id}/reimport?limit=N`；前端控件放在**会话标题栏**
  （与"取消关注"同一栏），条数输入默认值取该会话自己存的条数，结果用 notify 播报。
  输入框与按钮都用 h-10（`Input` 基类写死了 `h-10 w-full`，按 AGENTS.md 那条
  "不要用冲突类覆盖"的规矩，宽度由外层 `w-20` 容器控、按钮配同高的 default 尺寸）。
- 请求超时：后端命令等 300 秒，前端 `LONG_REQUEST_MS` 310 秒要等得比它久。

## 阶段五：引用消息改为"存定位 + 点击跳原文"（2026-10-14）

### 先做 Assumption Analysis，方案被自己改小了两处

用户提的目标是"和微信做得差不多：不存被引全文，存定位，点击跳原文"。动手前先把
假设摊开验，结果**原方案有两块被砍掉**：

- **不给 `messages` 加 `server_id` 列**。实测 `sort_seq` 在会话内唯一，它本身就是
  翻页游标 → 只要采集时把被引的 `svrid` 反查成 `quoted.sort_seq` 就够了。
  成本从"每条消息都补查"降到"只有引用行要查"，还不动 schema、不为这一列删库。
  **而且更鲁棒**：反查的是微信的分片库，原文还在我们导入窗口外时同样查得到；
  原方案依赖"我们库里已有那行"，那 3 条窗口外的引用就永久跳不到。
- **不加 `around` 新接口**。`before_seq = 目标+1, before_id = 1` 就能取到包含目标的
  那一屏（`before_id` 给 0 会被 API 的 `ge=1` 挡成 422 —— 踩过一次）。

## 阶段二·修 bug：图片解密下放轮询 + 微信后启动自动接上（2026-10-15）

### 症状（用户报）

微信没启动时先把服务开起来，随后再打开微信，前端**消息列表和设置页一起一直转圈**。

### 真实机制（两条线索叠在一起）

1. **钥匙分两把**。数据库钥匙（读文字）有落盘副本 `keys.json`，服务先启动也能连上；
   图片 AES 钥匙要靠微信运行时的 `cfg_dword` 现推（`MD5(str(cfg)+wxid)[:16]`），
   服务先启动时微信不在，`extract_master_key()` 便宜地返回 None → `cfg_dword=None`。
2. **缺钥匙的分支不是"报错"，是"抢"**。上游 `MediaDownloader._resolve_aes_key()`
   派生不出钥匙时走 `_scan_aes_key(monitor=True)`：整块读 Weixin.exe 内存、逐候选
   AES 试解，扫不到每 2 秒重扫、最长 120 秒。
3. 而这一串是在**回答网页请求的那条线路上**跑的（`api.py:_link_media` 读取时顺便补
   图片链接）。Python 一个进程只有一条线路能真正干活（GIL），它被内存扫描占住时
   连"读自己库"的 `/api/settings` 都要排队 → 两个页面一起转圈。
4. 附带两个同族坑：`open_isolated_db` 抛错后读线程 `return` 退出，用户之后打开微信
   也接不上，只能重启服务；微信运行中新建 db 文件时上游 `_refresh_db_files()` 会在
   采集线程里再来一次整进程扫描（`extract_keys()`）。

### 这一轮定的形状

| 事 | 放哪 | 频率 |
|---|---|---|
| 读文字消息 | 采集线程 | 每轮（现有逻辑不动） |
| 定位/解密/落盘图片 | **采集线程**（`_catchup_images`） | 每轮，限量 30 行，只认关注会话，新→旧 |
| 弄图片钥匙 | **采集线程**（`_ensure_media_key` → `prepare_key`） | 冷却 ≥120 秒，一次 `monitor=False` 扫描后落盘 |
| 网页请求 | 纯读自己库 | 毫秒级，**不碰 media、不碰上游库** |

- `api.py` 删掉 `_link_media` 与 `session_user`（会话 ID 解析归 `wechat.py`）。
- `ImageStore` 加**钥匙闸门**：`key_ready` 为假时 `attach()` 直接返回 None，
  连 `decrypt_image` 都不进 → 任何调用方（包括将来的新代码）都不可能顺手触发扫内存。
  钥匙来源按"免费优先"：cfg 派生 → 上次扫下来的 `image_keys.json` → 才扫一次内存。
- `Collector` 状态机加 `waiting_wechat`：连接失败**不退出线程**，轮询按 10 秒冷却重试；
  "微信没开"和"微信开着但读不通"在界面上说不同的话（前者琥珀色提示，后者仍算异常）。
- 未连接时命令**立刻**抛中文错误（`_request` 加 `self._wx is None` 判据）。原来只判
  "线程活着"，线程活着但没连上时命令会进队列永远没人执行，网页干等 90 秒超时。
- `catalog()` 的回落判据从"线程活着"改成"连着微信"；`reimport()` 不再自己重复判线程。
- 补图查询用 `instr` 粗筛而**不用 `json_extract`**：metadata 是文本列，一行坏 JSON
  会让 `json_extract` 抛错，而这条查询每轮都跑，不能因为一条写坏的行把整轮打死。

## 阶段二·补刀：图片"要等一分钟才出现"是冷却被白问了占掉（2026-10-15）

用户复测后回报：服务先开、微信后开，图片**过了将近一分钟才出现**。转圈没了，但延迟还在。

### 原因（我上一轮写错的判据）

`_ensure_media_key()` 把两件成本完全不同的事共用了**一个** 120 秒冷却，而且
`self._next_key_at = now + 120` 写在 `wechat_running()` 检查**之前**：服务启动后第一轮
（微信没开）只是便宜地问了一句进程表，却把 120 秒的重活冷却一并占掉了。用户随后打开微信，
采集线程要等冷却到期才会去取钥匙 → 白等最多两分钟。

### 改法：两把时间分开

| 动作 | 成本 | 节流 |
|---|---|---|
| `wechat_running()` 查进程表 | 毫秒级 | `MEDIA_KEY_PROBE_SECONDS = 5.0`，勤问 |
| 重连取 cfg / 扫内存找钥匙 | 几十秒级 | `MEDIA_KEY_RETRY_SECONDS = 120.0`，只在**真要动手时**才占用 |

先探测、再判冷却、最后才占用：微信一开 ≤5 秒就开始取钥匙，剩下的一次性成本只有
上游 `extract_master_key()` 读 `weixin.dll` 映像找锚点那几十秒（不改上游就去不掉）。

### 顺带把钥匙落盘补全

上游只在"扫内存扫到了"那条路径落盘 `image_keys.json`，cfg 现派生的那份不落盘 →
下次服务在微信没开时启动，还得重走一遍取 cfg。现在 `_adopt` 到 cfg 派的钥匙就顺手落盘
（从缓存读来的不重复写）。微信重启后钥匙会变，而 `_load_persisted_key()` 取用时会自校验，
所以过期缓存不会将错就错。

### 验证
- `pytest` 93 passed / 6 skipped。新增与改写的守门断言：
  `test_no_wechat_does_not_burn_the_heavy_cooldown` —— 微信没开那一次**不得**占用重活冷却
  （`_next_key_at` 保持已到期），且只留下一次便宜探测；紧接着把"微信在跑"打开、探测时间一到，
  必须**立刻**重连。这条断言就是本轮 bug 的直接反面。
  `test_cfg_derived_key_is_persisted_for_next_time` —— cfg 派的钥匙落盘、缓存来的不重写。
- 待用户复测：微信关掉 → 开服务 → 再开微信，看图片是不是在十几秒内出现（而不是接近一分钟）。

## 阶段二·再补刀：一个进程不许有两个读取器（WinError 5）（2026-10-15）

用户按"关微信 → 开服务 → 开微信"复测，报出红条：
`微信采集异常：[WinError 5] 拒绝访问。'...contact__contact.db.10964.593c.tmp' -> '...contact__contact.db'`
（随后下一轮自愈，状态回到 connected）。

### 原因

是我上一轮加的"重连取 cfg"引出来的：`_ensure_media_key()` 在 `cfg_dword` 缺失时
`_detach()` + `_attach()`，等于**在同一进程里开了第二个 `IsolatedDB`**。上游的建库锁
登记表是 `self._build_locks`——**按实例存**，不是按文件路径全局存。两个实例各自以为
自己在串行重建，实际会同时对 `data/wechat/cache/<指纹>/contact__contact.db` 动手：
新实例 `os.replace(tmp → dst)` 时旧实例还挂着 dst 的只读句柄，Windows 直接
`ERROR_ACCESS_DENIED`。这与 AGENTS.md 早就写着的"跑 capture_fixtures 要先停服务"
是同一类坑（同一份解密缓存不该被两个读取方同时开），只是这次是我们自己开的第二个读取方。

### 改法

1. **不再重连**：cfg 编号用 `self._wx.extract_master_key()` 从**当前**读取器要，
   拿到填回同一个对象（`self._wx.cfg_dword = got[1]`），随后 `prepare_key()` 免费派生。
   少一个实例、少一次全目录重扫，也少一次密钥校验。
2. **一次轮次失败不亮红条**：`_failures` 连计两轮才置 `error`。微信 checkpoint 期间
   上游重建缓存会短暂撞车，下一轮自愈；真没自愈的话"上次同步"时间会停着不动，那本身就是
   信号，不会漏报。

### 验证
- `pytest` 94 passed / 6 skipped。新增/改写：
  `test_media_key_takes_cfg_without_opening_a_second_reader`（`_attach`/`_detach` 必须
  一次都不被调用，`cfg_dword` 填回同一对象）、
  `test_no_wechat_does_not_burn_the_heavy_cooldown` 同步改成"不重开读取器"，
  `test_round_failure_needs_two_in_a_row_to_show_as_error`（一次失败不置 error、
  连续两轮置 error、自愈后清掉）。
- 待用户复测：同一条顺序（关微信 → 开服务 → 开微信）不再出现 WinError 5 红条。

## 阶段二·新功能：会话内消息搜索（2026-10-15）

### 需求（用户定义）

- 前端：搜索框宽度由外层 `span` 给（`Input` 基类是 `w-full`，同槽位塞两个宽度类会看
  样式表顺序）；停 300 毫秒再发请求，边打字不连发；`hits === null` 才表示"不在搜索态"，
  空数组是"搜了没搜到"，两者不能混。换会话**必须**退出搜索态（关键词属于上一个会话）。
- 点结果跳上下文**复用引用跳转那条路**：`sort_seq` 在会话内唯一，
  `before_seq = 目标+1, before_id=1` 取到含目标的一屏，再 `setFlashId` 描边滚过去。
  所以 `jumpToQuote` 改名 `jumpToMessage(target, fromSearch)`，两处共用，不新增接口。

## 阶段二·新功能：预览图重扫升级（"预览图怎么才能变成本机图"）（2026-10-15）

### 需求（用户提出）

问的是"预览图怎么才能变成本机图，当前有这个逻辑么"。查下来答案是**没有**：
`_catchup_images` 只补"从没有到有"（SQL 粗筛就是 `instr(metadata,'"local_file"') = 0`），
一行一旦拿到链接就永久出队。所以用户后来在微信里点了"查看原图"、`_h.dat` 已经躺在盘上，
我们也不会回头看一眼，气泡上一直挂着"预览图"。

### 边界（本机改变不了的那一半）

大那份文件不是我们能变出来的：只有**用户在微信里点开那张图**（原图还要多点一次
"查看原图"），微信才会把 `.dat` / `_h.dat` 落到 `msg/attach`。上游
`download_image_original()` 确实能自己去点界面，但那与"采集只读、不驱动 GUI"的约定
直接冲突（需要前台桌面、单张几十秒、还可能点错），**明确不采用**。所以这一轮做的是
**定期重扫磁盘追上去**：文件一到，链接跟着升。

另一个要说清的语义：中间那档 `.dat` 是"微信下发的那一份"，它可能是完整图、也可能
本身就是预览版，**本机三档里没有任何一档能证明它不是预览版**（上游实测结论）。
所以升到 `mid` 不等于画质上去了，只有 `_h.dat`（原图）才是确定的终点；角标文案继续
用"本机图"，不夸大成"高清图"。

### 做法

- `storage.stale_tier_images(limit=200)`：关注会话里"有链接、但档位还不是
  `"tier": "original"`"的图片行，新→旧。候选**不止 thumb**——停在 `mid` 的行以后点了
  原图也得能跟上去，所以终点定为 original。
- `Collector._upgrade_images()`：每轮真扫 10 行（`TIER_UPGRADE_LIMIT`），凭 metadata 里
  已有的 `media_md5` 再 `attach()` 一次（纯扫目录 + 本地解密，**不碰上游库、不碰界面**，
  钥匙闸门照旧），档位比现在高才改写 metadata，并 `ImageStore.discard()` 删掉替下来的
  旧图，媒体目录不堆孤儿。顺序是**先写库再删文件**：中途崩了最多留一个没人引用的文件。
- 两个数字分开：候选窗口 200 行 vs 每轮真扫 10 行。因为清单新→旧，而"用户从没点开过"
  的行永远升不上档，若不设冷却就会每轮拿同一批最前的行去翻整棵附件树、后面的永远排不到。
  冷却表在内存里（`{行 id: 下次允许重扫的时间}`，`TIER_RETRY_SECONDS = 600`），
  扫过没升上的才记，升上的立刻出队；重启即清空，无害也不动库结构。
- 前端一行没改：角标本来就照 `tier`/`tier_label` 画（`components/message.tsx`），库里
  一升级标记自己消失。存量**不需要清库重采**：新逻辑只是每轮多扫一遍，对已有行直接生效。

### 验证

- `pytest` 105 passed / 6 skipped。新增 6 条：候选清单收"有链接未到原图"的行（不含未链接
  的、不含未关注会话的）；`tier_rank` 的高低与原图/本机图/预览图/认不出四档；换档时改写
  链接 + 删旧文件；仍是预览图时一个字都不改且进冷却（第二次跑不再扫这一行）；已到原图与
  未连接的行一行都不扫；`discard` 对越界链接静略过。
- 真机（重启服务后几分钟）：关注会话里**预览图 7 行 → 4 行**，其中
  `1792072387002`、`1792072388000` 升到本机图（87KB / 51KB），`1792054822001` 直接升到
  **原图**（`_h.jpg` 205KB）；替下来的 3 个 `_thumb.jpg` 已删，媒体目录总文件数仍是 27
  （加一个新的一份删一个旧的，不涨孤儿）。剩下 4 行经目录直查确认本机**只有** `_t.dat`，
  判成"暂无更高一档"正确。`GET /media/…_h.jpg` 200、`/api/status` 为 connected、
  日志无 error。
- 采集线程每轮现在做四件：同步目录 → 轮询关注会话 → 补链接 → 重扫升级 →（缺钥匙时）补钥匙。

## 收尾补丁：wxgf 图片转码兜底（2026-10-16）

审核轮我在 HANDOFF 里写过"重采后当前 200 行里一张 wxgf 都没有"，那句**只覆盖了当时关注
的两个会话**；用户随后关注「文件传输助手」，53 条里就有 5 张是 `.wxgf` 破图。先把那句
错的更正掉，再修根因。

根因（本机逐层实测，不是猜的）：ffmpeg 装了、上游 `_ffmpeg_exe()` 也找到了、
`_extract_hevc()` 从 3091 字节的 wxgf 里剥出 2779 字节 HEVC 裸流，但上游把裸流写成

2. `enable_thinking`（官方 API 参考里列的那个）与 `thinking={"type": …}`

3. 开思考的单次耗时在 **0.9～29.9 秒**之间晃（同一条 prompt），而 64 token 的上限

## 阶段三·第一轮提炼：消息 → 任务（2026-10-17）

用户给了 `content.md`（不进 git）里两轮提炼的 user_content 与期望回复形状，本轮**只做第一轮**。
四个点先问后定：触发方式=**手动 + 独立后台线程**、进度记法=**messages 加 `extracted_at` 列**、
交付范围=**只做后端**、系统提示词=**我按契约新写**。

### 实现（三层，判据仍是"谁有权碰什么"）

- `niannian/extract.py`——**输入契约，全纯函数**：`render()` 出 XML（`<context>` →
  `<session name>` + `<history>`（**不带编号**）+ `<messages>`（`id="0..N-1"`））、
  `SYSTEM_PROMPT` 是判定规则、`parse_tasks()` 把回复收成任务。不碰库、不出网，
  所以提炼线程和测试都能直接打它。
- `niannian/extractor.py`——**轮次**：`Extractor.start(session_id)` 起一条 `extractor`
  线程，同时只允许一轮（`accepted=false` 表示上一轮还没结束，不排队）。按会话分组、
  每批 `BATCH_LIMIT=20` 条、一轮最多 `ROUND_LIMIT=200` 条、上文 `HISTORY_LIMIT=15` 条。
  **一批一次请求，失败不标记这批**：下一轮照旧取到它们，不会静默吞消息。额度与超时
  照"测试连接"那样分两档（关 1200/60s、开 2400/180s）。
- `storage.py`——新表 `tasks`（title/description/deadline/priority/status/sources，
  两个 CHECK 认三档优先级与三种状态）+ `messages.extracted_at`；
  **`commit_extraction()` 把任务与标记放同一个事务**：分两个事务的话崩在中间会把同一批
  再喂一次、再建一遍重复任务。投影列那套老库检查把 `extracted_at` 也带上
  （`EXTRACTION_COLUMNS`），缺列直接说"删掉重采"。
- `api.py`——`POST /api/extract`（起一轮，**出网前**先校验配置，没填 Key 直接 400）、
  `GET /api/extract/status`、`GET /api/tasks`。界面这一轮没接（用户定"只做后端"）。

### 几条语义是怎么定的

- **判据用 `extracted_at` 而不是会话级游标**：会话一旦被"重新导入"，更旧的消息会排在
  游标下面、永远轮不到；按每条消息自己有没有喂过模型来判就没这个问题（用例
  `test_reimported_older_messages_still_get_extracted` 钉住）。
- **任务依据落 `sort_seq` 不是批内编号**：编号只在那一次请求里有意义；`sort_seq` 会话内
  唯一、也正是翻页游标，界面点依据跳原文要照消息列表那条路走，不需要新接口。
- **引用只当定位**：渲染只读 `content`（气泡那行字），`metadata` 一概不进输入。
- **时间进出都是上海本地**：进模型的 `time` 形如 `2026-10-11T15:34`（**不带 `+08:00`**，
  时区在系统指令里说一次），库里 `created_at` 仍是 UTC，换算只在渲染这一头。
  落库的 `deadline` 统一成 `2026-10-13T00:00+08:00`。
- **不猜的东西一律丢掉而不是补**：`priority` 认不出当 medium（不把不确定的喊急）、
  `deadline` 认不出留空、标题为空或编号全越界的任务**不入库**（指不出依据的任务是编出来的）。
  `parse_deadline` 得自己拆形状：模型示例那个 `2026-10-13T0:00` 是个位小时，
  3.13 的 `fromisoformat` 直接拒（实测）。
- 图片这一轮**只喂 `[图片]` 那几个字**，`llm_include_images` 仍然没有任何代码读它。

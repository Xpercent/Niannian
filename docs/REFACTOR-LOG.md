## 修复：微信发送者名字解析错误（2026-10-14）

**症状**：群聊出现根本不是群成员的署名（"吴寒"16 条、"助班学长"1 条），私聊里自己发的消息全部署上对方名字（王五月会话 100 条只有 5 条
`is_self=1`）。原版没这个表现。

**根因**：微信 4.x 消息分片库中 `Msg_*.real_sender_id` 是**该分片库自身 `Name2Id` 表的 rowid**，id 空间按分片各自编号；上游
`wechatauto.db._sender_id_index()` 却用 `message_resource.db` 的全局 `SenderName2Id` 去解析（全库没有任何一处用到正确的分片 `Name2Id`），
于是 `sender_username` 是**另一个人的 wxid**——实测本群 `real_sender_id=5` 分片内是"我自己"，全局表解析成"吴寒"。正文带 `wxid_x:` 前缀的
行（群聊普通文本）被 `split_sender` 的前缀救回，所以看着是对的；**没有前缀的行全部落到错误映射**：自己发的文本、emoji、图片、系统消息。
私聊完全没有群前缀，故 `is_self` 恒为 0。原项目有同一处缺陷（同版本子模块、同样的 `origin or sender_username` 优先级），只是它只导入过"全
员带前缀"的通知群（180 条 `is_self` 全为 0），症状未暴露。

**当时的改动**（只在 `niannian/wechat.py`，**不动子模块**——它是 detached HEAD 的第三方锁定）：新增 `sender_alias_map()` 在分片内按
`(sort_seq, local_id)` 联合 `Name2Id` 还原真实发送者；`IsolatedDB._fix_senders()` 覆写 `get_messages`/`get_new_messages`，分片解析不到的
行把 `sender_username` 置空；`normalize_message` 的发送者优先级由「正文前缀优先」改为「**分片解析优先、正文前缀兜底**」。

> 后续：1、2 两条已在 2026-10-14 删掉——上游 1.2.6.1（issue #34）自己按分片解析了，见「子模块升级到 1.2.6.1」。第 3 条仍然有效。

**验证**：pytest 14 项通过。真机清库重采：群 100 条署名全部落在该群 4 名真实成员内，原 16 条"吴寒"→"我"；私聊 `is_self` 由 95/5 变为分布
自然的 56/44；89 条带前缀的行前缀与分片解析零冲突。**残留**：拍一拍 appmsg 的 `real_sender_id=9` 在 `Name2Id` 中 `user_name` 为空，回落显
示"群成员"（原版同场景错显示为"助班学长"）；空名系统类消息的署名策略待用户定。

## 阶段二：图片显示（2026-10-14）

**目标（用户定义）**：让图片能显示出来；库里**只落图片本地链接**；清库重新采集。用户另外指出：原版对"没在微信里手动点开过的图片"处理有问题
——那些其实有预览图文件、能被解析出来，但原版没做。

**实测到的三条事实**（规则见 AGENTS.md「图片附件的关键事实」）：

1. **磁盘文件名哈希只在 `packed_info_data` 里**。正文 XML 的 `md5` 属性是另一套值：实测 `md5="6793b97e…"` 那条图，磁盘文件叫
   `3d11d910dfa03787d8b96a2964079fd2_t.dat`。按 XML 的 md5 去 attach 目录找，23 条一条都找不到。
2. **未点开过的图片只有 `_t.dat` 预览图，且能解出来**（单字节 XOR，从文件尾 `FF D9` 反推密钥，不需要图片 AES 密钥）。实测两个会话 23 张图：
   原图 9 / 本机下发那份 6 / **只有预览图 8**。上游 `download_image(tier='best')` 本来就会回落到预览图档，所以"能不能解"不是问题，问题在
   **什么时候去解**。
3. 原版把提取只挂在采集那一刻（`MediaCache.enrich` 在 `_store` 里调用一次），而微信的预览图是**翻到那条记录才落盘**的。它自己的库里就有证据：
   `45948752706@chatroom` 28 条图片只有 8 条留下 `local_file`，而今天对这 32 条重跑 `tier='best'` 是 **32/32 全部可解**——文件一直在盘上、
   能解析，库里却没链接。

**改动**：新增 `niannian/media.py`（未搬运原版）：哈希补查、`pick_tier`（`_h.dat` 小于 1KB 视为下载中断空壳）、`ImageStore.attach` 只回传
相对链接、`safe_media_path` 收口。入库正文换成 `[图片]`，尺寸留在 metadata 不进摘要（`cdnthumb*` 是预览图尺寸，标出来会误导）。`api.py`
当时加了 `GET /media/{name}` 与**读取时**凭 `media_md5` 补链接回写库的 `_link_media`（后者在"图片解密下放轮询"一轮删掉）。

**验证**：pytest 22 项通过。真机清库重采 200 条消息、23 条图片**全部**拿到本机链接（原图 9/本机图 6/预览图 8）；预览图 URL 返回 200
`image/jpeg`（`FF D8 FF`，118x210）、原图返回 200 `image/png`；`../`、`%2e%2e%2f`、盘符、`/etc/passwd`、三段穿越五类越界探测全部 404。

**已知边界**：只处理图片，视频/语音/文件/卡片/拍一拍仍入库原始 XML；预览图放大后仍模糊，弹窗标注"预览图"不假装是原图——要真原图必须让微信
去下载，那属于驱动界面，超出只读边界；回填只认采集时已写入的 `media_md5`（本轮已清库重采，库内不存在没有该字段的老行）。

### 阶段二补丁：图片档位标注与放大弹窗尺寸（2026-10-14）

用户实机反馈三件事，根因两个（`cn()` 纯字符串拼接这条规则见 AGENTS.md「前端约定」）：

1. **横向图片的放大弹窗太小**：`Dialog` 基类写死了 `max-w-lg`，调用方再传 `max-w-3xl` 会让两个宽度类同时挂在元素上，谁生效取决于样式表顺序
   ——实测基类赢了，弹窗被钉在 512px，横图被 `max-h` 夹住后左右全是空白，所以"横图小、竖图正常"。改为基类**不再写死宽度与内边距**，由
   `width` / `padded` 两个 prop 整档给出。
2. **预览图和正常图放大到一样大，糊得看不清**：弹窗 `<img>` 带了 `w-full`，等于把 118x210 的预览图强行拉到满宽。去掉 `w-full`，只用
   `max-w-full` + `max-h-[74vh]` 夹住、`w-auto` 保持原始尺寸，弹窗 `w-fit` 收到图片实际大小——大图照样撑到 `min(1200px,94vw)`。
3. **预览图要在气泡上就标出来**：缩略图左上角加"预览图"角标，只在 `tier === 'thumb'` 时出现（原图/本机图不打标，避免给每张图都加噪音）。

验证（内置浏览器量几何，视口 715x778）：9 个图片气泡中角标只出现在 5 个预览图上；横向 1920x1080 的图弹窗 668x410、图片 666x375，无放大无裁
切；预览图 118x210 弹窗收紧到 141x245；`关注会话` 弹窗仍是 512x626 + p-6 + Esc 可关，基类改动无回归。

## 阶段二补丁：群名片一档与系统消息署名（2026-10-14）

起因：用户问「群内昵称能不能获取到」。答案是能，而且拿到之后发现现有显示规则**少了一档**。

**实测结论**（规则见 AGENTS.md「发送者显示名」）：群名片**没有独立表列**（`chatroom_member` 只有 room_id + member_id），它藏在
`chat_room.ext_buffer` 的 protobuf 里（字段 1=成员 wxid、2=群名片、4=邀请人），上游 `get_group_members()` 从没解析过这个 buffer；实测
`45948752706@chatroom` 32 名成员有群名片，宿舍群 `50333318698@chatroom` 0 人设置过。微信自己的优先级是 **备注 > 群名片 > 昵称**，依据不是猜
的：拿微信算好的 `session.db.SessionTable.last_sender_display_name` 与三方逐一比对，7 例「群名片/备注/昵称互不相同」的样本里 6 例（无备注）
跟随群名片、1 例（有备注，`助班学长` vs 群名片 `厦门黄宸溢（26软2助班）`）跟随备注。原逻辑（沿用原版）是 `备注 > 昵称`，**中间那档被跳过**；
原项目带着同一个错，证据在它自己库里：`workspace.db` 存着 `sender_name='五大天王-陈德华'`（全局昵称），而微信在该群显示的是
`科技委员21陈永源`（群名片）。

**改动**：新增 `niannian/contacts.py`（`protobuf_fields` 只支持 wire 0/2，遇到别的类型就停，不猜偏移量把后面的数据当字段读；`display_name`
是三档定序的唯一实现）；`IsolatedDB.display_names(user)` 按会话现算三档替代全局 `nickname_map()`。**无发送者的行**（`Name2Id.user_name` 为
空：拍一拍、撤回、进群提示）署名 `系统消息`、`sender_key` 置空不参与按人归组（原来回退成 `群成员`，更早是错标成某个群外成员）。顺带修掉群自
己发的系统行正文前缀是**群 ID**（`45948752706@chatroom:`）导致入库正文带裸群 ID 的问题——现在剥掉但不认作发送者。

**验证**：pytest 30 项通过。真机清库重采 3 个会话共 300 条：通知群署名变成 `学委陈晔显 / 科技委员21陈永源 / 文体委员吴彦朋 / 宣传委员46彭怡
珍`；宿舍群不变（无人设群名片）；私聊 `王五月 53 / 我 44 / 系统消息 3`。把库里每个 `(会话, sender_key) → sender_name` 与 `display_names()`
现算值逐条比对，**不一致 0 条**；裸群 ID 前缀残留 0 条；39 张图片链接正常。

## 阶段二补丁：读路径按时间排序 + 每会话独立的重新导入（2026-10-14）

用户要"导入更早历史"的入口。先出方案时我把它做成了完整链路（上游 keyset 翻页 + 新命令 + 新字段 + 到底判断 + 防连点），用户明确否掉：**该功能
非刚需，不要把系统搞复杂**。最终只做两件便宜的事，明确不做无限往回翻页。

**关键发现：真正的工作量不在"取更旧的消息"。** 现有 `messages_page` 按**自增 id 倒序**翻页，游标是 `before_id`。它能成立纯粹是因为消息永远"新
的后入库"，id 顺序刚好等于时间顺序——这是巧合不是设计。一旦重新导入，更旧的消息会带着**更大**的 id 插进来，按 id 排顺序就翻了。所以"改排序"
是必须先还的债，而不是可选优化。

**A 读路径按时间排序**（规则见 AGENTS.md「消息顺序与重新导入」）：排序键换成 `(sort_seq DESC, id DESC)`，游标换成 `(before_seq, before_id)`
复合，索引换成 `(session_id, sort_seq, id)`。同一 `sort_seq` 并列时用 id 做稳定 tiebreak（跨分片 `local_id` 本身会重复，没有更可靠的列能破
并列，**接受同秒内按入库先后**）。旧库若保留索引定义不会自动换（`CREATE INDEX IF NOT EXISTS`），但排序是显式写在 ORDER BY 里的，**只影响性
能不影响正确性**。本轮按惯例清库重采。

**B 每会话独立的重新导入**：`sessions.history_limit` 新列，**0 表示跟随全局默认**，刻意与全局 `history_limit` 分开：调某一个会话不该影响其它
会话（用户明确要求）。`Collector.reimport` 走已有命令队列进采集线程（只有它碰上游库），= 记下条数 → 清水位 → 复用 `_import_recent`；**不删任
何已入库消息**，重复行由 `source_id` 唯一键跳过。后端命令等 300 秒，前端 `LONG_REQUEST_MS` 310 秒要等得比它久。

**验证**：pytest 34 项通过。真机清库重采后对宿舍群点重新导入 400：返回"读到 259 / 新增 159"（该群总共就 259 条，已探到最旧），逐页翻到底共
7 页 259 条，**无重复、时间倒序违例 0**；三个会话里只有被操作的那个 `history_limit=500`，另两个仍是 0；该群水位仍停在最新 sort_seq，**没被
更旧的回填拉回去**；回填消息的图片自动补了链接（全站 39 → 45 张）。**明确没做**：无限往回翻页（需要上游 keyset 查询、新命令、"已探到最旧"标
记、防连点，等 1000 条真不够用再说），因此**单次重新导入的上限仍是 1000 条**（`clamp_history_limit` 的天花板）。

## 阶段三起步：设置页（2026-10-14）

范围（用户定的）：先盘清了"现在到底有哪些参数能设"，用户从候选里只挑了 `history_limit`、`poll_seconds`、`port` 三项，其余（监听地址、微信数据
目录、微信账号、各类内部上限）**不进设置页**，仍可手工写在 `config.json`。`host` 刻意不开放：改成非 `127.0.0.1` 等于把本机微信聊天记录暴露到
局域网，而且改错会把自己关在门外（服务起来了但打不开）。模型那五项是「模型接入」一轮才加进来的。规则见 AGENTS.md「设置页与配置」。

- **生效方式：混合，界面如实标注。** `Collector` 构造时拿的是 settings 的**副本**（`dict(settings)`），只改 `app.state.settings` 传不到采集器：
  `history_limit`/`poll_seconds` 写盘后调 `Collector.update_settings()` 推进采集器自己的副本（每轮重读间隔、每次导入重读条数，立即生效）；
  `port` 只能重启，界面标"需重启"并额外给一条横幅说明"重启后请用 http://127.0.0.1:新端口 访问；起不来就手工改回配置文件"——不假装已应用。
- **校验：读宽容、写严格。** `load_config` 坏值退回默认或夹到边界（保证服务起得来），`validate()` 只在保存时用，越界直接抛中文错误、不落盘；
  两者分工不同，是有意的。`save_config()` 只更新提交的键、**保留文件里已有的其它键**，先写 `.tmp` 再 `os.replace`。**故意不设
  `SO_REUSEADDR`**：`port_busy()` 加了它，Windows 下那个选项允许重复绑定正在监听的端口，探测会假成功。
- 顺带：`Badge` 加 `tone` 档（`cn()` 是纯拼接，`className="bg-amber-100"` 压不住基类的 `bg-secondary`）；修一个切页丢状态的缺陷——选中会话从
  `SessionsPage` 内部提升到 `App`。

**验证**：pytest 51 项通过（新增 17 项配置层测试：8 种越界/非法输入的中文报错、保留其它键、不留临时文件、读时仍宽容、只有 port 需重启）。真
机：`history_limit=5000` → 400 "导入条数要在 1 到 1000 之间"；改成正在监听的端口 → 400 "端口 4001 已被其它程序占用，换一个"；**热更真的生
效**——`history_limit` 存成 200 后新关注一个群，入库正好 200 条（默认是 100），旧会话仍是 100/259 不受影响。

## 阶段四：非文本消息格式化（2026-10-14）

### 先摸清家底（不猜，全部实测）

清库前库里 659 条，其中 **156 条正文还是 XML 原文**（图片那 52 条上一轮已经变成 `[图片]`）。逐条过了一遍，形状分布是：

| 上游标签 | 实际是什么 | 条数 | 判据 |

**症状（用户报）**：微信没启动时先把服务开起来，随后再打开微信，前端**消息列表和设置页一起一直转圈**。

**真实机制（两条线索叠在一起）**（定论见 AGENTS.md「钥匙与线程」）：① **钥匙分两把**——数据库钥匙有落盘副本 `keys.json`，服务先启动也能连上；
图片 AES 钥匙要靠微信运行时的 `cfg_dword` 现推（`MD5(str(cfg)+wxid)[:16]`），微信不在时 `extract_master_key()` 便宜地返回 None。
② **缺钥匙的分支不是"报错"，是"抢"**——上游 `_resolve_aes_key()` 走 `_scan_aes_key(monitor=True)`：整块读 Weixin.exe 内存、逐候选 AES 试解，
扫不到每 2 秒重扫、最长 120 秒。③ 而这一串是在**回答网页请求的那条线路上**跑的（`_link_media` 读取时顺便补链接）；一个进程只有一条线路能真正干
活（GIL），它被内存扫描占住时连"读自己库"的 `/api/settings` 都要排队 → 两个页面一起转圈。④ 两个同族坑：`open_isolated_db` 抛错后读线程
`return` 退出，用户之后打开微信也接不上，只能重启服务；微信新建 db 文件时上游 `_refresh_db_files()` 会在采集线程里再来一次整进程扫描。

**这一轮定的形状**：

| 事 | 放哪 | 频率 |
|---|---|---|
| 读文字消息 | 采集线程 | 每轮（现有逻辑不动） |
| 定位/解密/落盘图片 | **采集线程**（`_catchup_images`） | 每轮，限量 30 行，只认关注会话，新→旧 |
| 弄图片钥匙 | **采集线程**（`_ensure_media_key` → `prepare_key`） | 冷却 ≥120 秒，一次 `monitor=False` 扫描后落盘 |
| 网页请求 | 纯读自己库 | 毫秒级，**不碰 media、不碰上游库** |

要点：删掉 `api.py` 的 `_link_media`；`ImageStore` 加**钥匙闸门**，任何调用方都不可能顺手触发扫内存；`Collector` 加 `waiting_wechat`（连接失败
**不退出线程**、10 秒冷却重试，"微信没开"和"微信开着但读不通"在界面上说不同的话）；未连接时命令**立刻**抛中文错误（原来只判"线程活着"，命令会
进队列没人执行，网页干等 90 秒超时）；`catalog()` 的回落判据从"线程活着"改成"连着微信"；补图查询用 `instr` 粗筛而**不用 `json_extract`**（一
行坏 JSON 会让它抛错，而这条查询每轮都跑，不能因为一条写坏的行把整轮打死）——`instr` 那一处后来在审核轮换成了投影列。**存量：不用清库重采**
——入库字段与解析都没动，只是**谁来补**换了；库里 8 条图片行 7 条已有链接、1 条待补。

**验证**：pytest 92 passed / 6 skipped（skip 的是 `test_capture_replay.py`，本机 fixture 不在）。四条守门：消息列表接口绝不碰 media（**谁把解
密挪回请求线程就红**）、闸门关闭时 `decrypt`/`scan` 一次都不许被叫到、扫内存必须 `monitor=False` 且只扫一次、读线程第一次连不上第二次连上能自
愈。真机（微信未开）：`/api/status` `/api/settings` `/api/sessions` 2–14 ms、消息列表 4 ms、已链接图片 `/media` 200（144 KB）；待补那 1 行保
持待补、没有产生任何内存扫描，`image_keys.json` 未生成。独立采集器模拟"本机读不到微信数据"：状态 `waiting_wechat`、10 秒后仍在重试、
`catalog()` 回落本地 `[]`、`reimport()` 立刻返回"微信还没连上：请打开微信，采集器会自动接上。"。**当时尚未跑真机的一条**：打开微信后钥匙自动补
齐（要用户实际操作微信）。顺带：前端默认超时从 120 秒降到 20 秒、会话目录 100 秒、重新导入仍 310 秒；图片占位文案改成"这张图片还没准备好：打开
微信、并在微信里翻到这条记录后会自动补上"——闸门关闭时文件其实在盘上但没钥匙，旧文案"本机暂无该图片文件"在这种情况下是说假话。

## 阶段二·补刀：图片"要等一分钟才出现"是冷却被白问了占掉（2026-10-15）

用户复测后回报：服务先开、微信后开，图片**过了将近一分钟才出现**。转圈没了，但延迟还在。

**原因（我上一轮写错的判据）**：`_ensure_media_key()` 把两件成本完全不同的事共用了**一个** 120 秒冷却，而且 `self._next_key_at = now + 120` 写
在 `wechat_running()` 检查**之前**：服务启动后第一轮（微信没开）只是便宜地问了一句进程表，却把 120 秒的重活冷却一并占掉了；用户随后打开微信，
采集线程要等冷却到期才会去取钥匙 → 白等最多两分钟。**改法：两把时间分开**——先探测、再判冷却、最后才占用：

| 动作 | 成本 | 节流 |
|---|---|---|
| `wechat_running()` 查进程表 | 毫秒级 | `MEDIA_KEY_PROBE_SECONDS = 5.0`，勤问 |
| 重连取 cfg / 扫内存找钥匙 | 几十秒级 | `MEDIA_KEY_RETRY_SECONDS = 120.0`，只在**真要动手时**才占用 |

微信一开 ≤5 秒就开始取钥匙，剩下的一次性成本只有上游 `extract_master_key()` 读 `weixin.dll` 映像找锚点那几十秒（不改上游就去不掉）。**顺带把钥
匙落盘补全**：上游只在"扫内存扫到了"那条路径落盘 `image_keys.json`，cfg 现派生的那份不落盘 → 下次服务在微信没开时启动还得重走一遍取 cfg；现
在 `_adopt` 到 cfg 派的钥匙就顺手落盘（从缓存读来的不重复写）。微信重启后钥匙会变，而 `_load_persisted_key()` 取用时会自校验，过期缓存不会将
错就错。验证：pytest 93 passed / 6 skipped；守门断言 `test_no_wechat_does_not_burn_the_heavy_cooldown`（微信没开那一次**不得**占用重活冷却，
紧接着"微信在跑"打开、探测时间一到必须**立刻**重连——这条断言就是本轮 bug 的直接反面）。

## 阶段二·再补刀：一个进程不许有两个读取器（WinError 5）（2026-10-15）

用户按"关微信 → 开服务 → 开微信"复测，报出红条：
`微信采集异常：[WinError 5] 拒绝访问。'...contact__contact.db.10964.593c.tmp' -> '...contact__contact.db'`（随后下一轮自愈，状态回到
connected）。

**原因**：是上一轮加的"重连取 cfg"引出来的——`_ensure_media_key()` 在 `cfg_dword` 缺失时 `_detach()` + `_attach()`，等于**在同一进程里开了第二
个 `IsolatedDB`**。上游的建库锁登记表 `self._build_locks` 是**按实例存**的，两个实例各自以为自己在串行重建，实际会同时对
`data/wechat/cache/<指纹>/contact__contact.db` 动手：新实例 `os.replace(tmp → dst)` 时旧实例还挂着 dst 的只读句柄，Windows 直接
`ERROR_ACCESS_DENIED`。这与"跑 capture_fixtures 要先停服务"是同一类坑，只是这次是我们自己开的第二个读取方。

**改法**：① **不再重连**——cfg 编号用 `self._wx.extract_master_key()` 从**当前**读取器要，拿到填回同一个对象（`self._wx.cfg_dword = got[1]`），
随后 `prepare_key()` 免费派生。② **一次轮次失败不亮红条**——`_failures` 连计两轮才置 `error`：微信 checkpoint 期间上游重建缓存会短暂撞车，下一
轮自愈；真没自愈的话"上次同步"时间会停着不动，那本身就是信号，不会漏报。验证：pytest 94 passed / 6 skipped（守门：`_attach`/`_detach` 必须一
次都不被调用；一次失败不置 error、连续两轮置 error、自愈后清掉）。

耗时毫秒级。**顺带发现（未改）**：`index.html` 由 `FileResponse` 直发、没带 `Cache-Control`，重新构建后浏览器可能仍用缓存里的旧入口 HTML（本轮

## 阶段二·新功能：预览图重扫升级（"预览图怎么才能变成本机图"）（2026-10-15）

**需求（用户提出）**：问的是"预览图怎么才能变成本机图，当前有这个逻辑么"。查下来答案是**没有**：`_catchup_images` 只补"从没有到有"（SQL 粗筛就
是 `instr(metadata,'"local_file"') = 0`），一行一旦拿到链接就永久出队——用户后来在微信里点了"查看原图"、`_h.dat` 已经躺在盘上，我们也不会回头
看一眼，气泡上一直挂着"预览图"。

**边界（本机改变不了的那一半）**：大那份文件只有**用户在微信里点开那张图**（原图还要多点一次"查看原图"）才会落到 `msg/attach`；上游
`download_image_original()` 确实能自己去点界面，但那与"采集只读、不驱动 GUI"的约定直接冲突（需要前台桌面、单张几十秒、还可能点错），**明确不采
用**，所以这一轮做的是**定期重扫磁盘追上去**。另一个要说清的语义：`.dat` 可能是完整图、也可能本身就是预览版，**本机三档里没有任何一档能证明它不
是预览版**（上游实测结论），所以升到 `mid` 不等于画质上去了，只有 `_h.dat`（原图）才是确定的终点；角标继续用"本机图"，不夸大成"高清图"。

**做法**（规则见 AGENTS.md「图片附件的关键事实」）：`storage.stale_tier_images(limit=200)` 取"有链接、但档位还不是 `"tier": "original"`"的行
（候选**不止 thumb**，停在 `mid` 的行以后点了原图也得能跟上去）；`Collector._upgrade_images()` 每轮真扫 10 行（`TIER_UPGRADE_LIMIT`），凭已有
`media_md5` 再 `attach()` 一次（纯扫目录 + 本地解密，**不碰上游库、不碰界面**），档位变高才改写 metadata 并 `ImageStore.discard()` 删掉替下来
的旧图，顺序是**先写库再删文件**（中途崩了最多留一个没人引用的文件）。两个数字分开：候选窗口 200 vs 每轮真扫 10；冷却表在内存里
（`TIER_RETRY_SECONDS = 600`），重启即清空、不动库结构。前端一行没改；存量**不需要清库重采**。

**验证**：pytest 105 passed / 6 skipped。真机（重启服务后几分钟）：关注会话里**预览图 7 行 → 4 行**，`1792072387002`、`1792072388000` 升到本机
图（87KB / 51KB），`1792054822001` 直接升到**原图**（`_h.jpg` 205KB）；替下来的 3 个 `_thumb.jpg` 已删，媒体目录总文件数仍是 27（不涨孤儿）；
剩下 4 行经目录直查确认本机**只有** `_t.dat`。采集线程每轮现在做四件：同步目录 → 轮询关注会话 → 补链接 → 重扫升级 →（缺钥匙时）补钥匙。

## 收尾补丁：wxgf 图片转码兜底（2026-10-16）

可 **0 是合法值**（不想带上文），哨兵和合法值撞在同一个数上，那种设计迟早出事。改成
`config.DEFAULTS` 直接引 `extract.DEFAULT_ROUND_LIMIT` / `DEFAULT_BATCH_LIMIT` /
`DEFAULT_HISTORY_LIMIT`（原来的三个裸常数改名加 `DEFAULT_` 前缀），**留空 = 用默认、填进去的
0 = 真的要 0**；前端 `numberOrNull()` 空框交 `null`，`extract.policy()` 只在键不存在或
读不出整数时回落。

**新形状 `extract.policy(settings) → Policy`**（NamedTuple：round/batch/history/prompt）。
`Extractor.start()` 起轮时取**一次快照**，`_run(sid, plan)` 与 `_one_batch(..., plan)` 全程用它：
一轮要跑几分钟，中途在设置页改批次或提示词不该让后半批换个问法，否则失败重跑时说不清是哪条
规则把 JSON 写坏的。这条钉了一条用例（第一批进请求后改 settings，仍按 2 条一切、system 不换）。

**提示词那一格的回显**：`GET /api/settings` 的 `values.extract_prompt` 回的是**正在生效的那段**
（库里空串意思是"用内置"），顶层另给 `extract_prompt_default` 供「恢复默认」按钮用。
`validate()` 里加了一条归一化：**提交的内容与内置一字不差就落空串**——否则 `config.json` 里会
躺一份副本，日后内置改了（比如又撞出一个要把 JSON 写坏的形状）会被自己存的那份挡住。
长度上限 8000 字；三个数的边界 1..1000 / 1..50 / 0..100，越界不落盘、说中文。

**设置页多一张「提炼」卡片**：三个数字格 + 一个 `rows=16` 的提示词文本框 + 标题栏那颗
「恢复默认提示词」。采集那三项与提炼这三项长得一样，把原来写在 map 里的那圈 JSX 抽成
`NumberField`，只在这两个卡片里各用一次（没有第三处，不提前抽象）。

**存量：不用清库重采**——四个键既不入库也不参与解析，下一轮读到的就是新形状。

**真机验过什么**：重启服务后打开 `#settings`，结构快照里三个数字格的 `valuemin/valuemax/value`
是 1/1000/200、1/50/20、0/100/15，文本框里就是内置全文 1200 字；填 51 保存 →
`PUT /api/settings` 回 **400** 且 `config.json` 里没落这个键；填 8 保存 → 落 `8`，
`extract_prompt` 保持空串、API Key 没被动；改回 20 保存；把文本框换成一句话再点「恢复默认」
→ 框里回到 1200 字且仍带着"字符串值里不能出现英文双引号"那句。**没看到的**：应用内浏览器没有
可见面板，截图拿不到，所以这张卡片的**像素与排版没验过**（只验了控件、值与回路）；保存后的那条
提示 toast 也没抓到文本。

`pytest` **267 passed / 6 skipped**（+23：`test_config` 11 条新键读写与边界、`test_extract` 4 条
policy、`test_extractor` 2 条设置生效与一轮快照、`test_api_settings` 4 条接口形状）、
`tsc --noEmit` 干净、`npm run build` 通过。

## 提炼诊断页：每批发出去什么、模型回什么（2026-10-20）

用户要的是：**写一个提炼诊断页面，能查看某轮的所有请求原始内容与模型回复结果**；
原项目**只参考 UI**（接口与数据那套不看），并且**不得添加多余功能**——只要发出去的请求
与模型的回复。

**先撞到的事实：库里什么都没留。** `Extractor` 的进度只在内存 `self.state` 里，
发出去的 `messages` 与 `chat()` 回来的那份文本在 `_one_batch` 里活不过一次函数调用，
所以"回查某轮的请求"这件事没有数据可查，得先让它落库。原项目那页有四个视图
（轮次追踪 / 调用检索 / 异常与拦截 / 滞留队列）外加校验对照与落库去向，
**这些一律没搬**——我们没有 `task_events`、没有 guard 改写、没有静默窗口，
搬过来就是为界面补空表。搬的只有那页的形状：左侧轮次列表 → 右侧请求序列 →
点开一条换成整宽的 inspector（返回 + 上一/下一条），里面两栏「发给模型的内容」
与「模型回了什么」，正文收在 `Fold` 里、`Code` 逐字显示。

**两张新表**（`storage.py`）：`extract_runs` 一轮一行（`total/done/created/failed_batches/error`
+ 起止时间），`model_calls` 一批一行（`request` 就是发出去那两条 message 的 JSON，
另存 `response`、`reasoning`、`error`、`model`、`messages`、`duration_ms`）。四件事定了形状：

- **列表不带正文。** `runs/{id}` 只回概要，字符数用 `LENGTH()` 现算——不多存一列就
  不会和正文漂开；点开哪一条才由 `calls/{id}` 取那一条的正文（一轮十几批、每批几 KB）。
- **进度每批同步一次**（`_sync_run`）：一轮要跑几分钟，等跑完才写库的话，跑到一半
  诊断页上这一轮是空的，看着像什么都没发生。
- **失败那批照样有行**，连服务商那句中文原因一起存。诊断要看的就是"那次到底发了什么、
  对方说了什么"，只记成功的那几批等于把最该看的部分删掉。
- **只留最近 30 轮**（`EXTRACT_RUNS_KEPT`），收尾时删超出的轮次，请求行靠
  `ON DELETE CASCADE` 跟着走。**地址与密钥不进这两张表**，也不出 `/api/diagnostics/*`。

`Extractor.status()` 多带一个 `run_id`，界面才知道哪一行是当下正在跑的那轮
（`finished_at` 空 + 不是当前轮 → 走"未结束"，不假装进行中）。三条新接口全纯读自己的库，
毫秒级，与"请求线程一律纯读"那条不冲突。

**存量：不用清库重采**——两张表是 `CREATE TABLE IF NOT EXISTS` 加的，起服务就补上；
代价只是补上之前的轮次没有正文可回查（界面上那句话写在页脚）。

**真机验过什么**：起了一个沙箱服务（`data/_diag_ui_check.py`：采集器换成替身、库在
`data/_diag_ui/`、灌两轮假留档），浏览器里逐屏看过轮次列表（含"有 1 批失败"那一行）、
请求序列（成功/失败两种行）、inspector 的两栏与三个 `Fold`（XML 默认展开、系统提示词与
原始 JSON 收起）、上一条/下一条步进、失败那条的"没有任何返回文本"那一支，以及空态。
**没看到的**：真机跑一轮之后的真实留档（要出网，等你点「立即提炼」）；
**桌面宽度下两栏并排的形状没验过**——验收用的浏览器视口只有 ~507px，看到的是单栏堆叠。

**要重启服务**：8765 上那个进程还是改动前的代码，而 `web/dist` 已经是新的，
这中间打开诊断页会读到 404。

`pytest` **274 passed / 6 skipped**（+7：`tests/test_diagnostics.py` 逐字留档形状、
列表不带正文、失败也记、跑一半就有进度、只留最近 30 轮 + 级联不留孤儿、三条接口、404）、
`tsc --noEmit` 干净、`npm run build` 通过。

**补（同日，用户看过界面之后）**：「模型回了什么」这一栏改成**读得成 JSON 就缩进显示**——
先剥代码围栏再 `JSON.parse`，成功就 `JSON.stringify(parsed, null, 2)`，逐字那一份收进
「原始回复（逐字）」折叠；**读不懂就照原样贴**并写明为什么不加工（半截 JSON 正是整批失败的
常见形状，为了好看替服务商补括号会把要看的东西藏掉）。缩进只发生在显示这一头，
库里存的仍是逐字那份，「复制原始回复」交的也还是逐字。沙箱里三种形状都看过：
正常一份、带 ```json 围栏的一份、半截 JSON 的一份。`npm run build` 通过，后端一行没改。


## 模型接入加温度：填了才发（2026-10-20）

用户要的"温度参数"落成一个键 `llm_temperature`。语义在两个方案里选了**留空 = 请求体里不带
`temperature`**（而不是替所有人发一个 0.7）：各家默认值不一样，而少数推理模型不接受这个字段，
替用户塞默认值就是给它们一条 400。这与同一天定下的"四道 `max_tokens` 全去掉、长度上限交回
服务商"是同一条思路。

- **0 与"没填"是两种值**：要完全不随机得真填 0，所以 `llm.py:chat()` 判的是 `is not None`
  而不是真假，前端空框交 `null`（复用 `settings.tsx:numberOrNull` 那一个出口）。
- 边界 **0~2 只有 `config.TEMPERATURE_BOUNDS` 一份**：`validate()` 严格（越界与"热"这种都抛
  中文错、不落盘），`load_config()` 宽容（读不出来当没填、越界夹到边界，服务照样起得来）——
  与那三个提炼数是同一套分工。
- 提炼**不需要新通道**：`Extractor` 每批现读 `settings` 调 `chat()`，温度与地址/模型名/思考开关
  同一档，不进 `extract.policy()` 那一轮快照（快照只管"这批怎么问"的三个数与提示词）。
- 「测试连接」的草稿也带这一格：界面上清空 → 草稿里是 `null` → 这一试照样不发，**不悄悄沿用
  库里那个旧的**（用例钉住）。

**真机验过**：Google 那家吃这个字段——设置页草稿带 0.5 点「测试连接」，2.6 秒回「好的」，没 400。
**没验的**：SiliconFlow/智谱那两家带温度的实际采样差异。库里这一格现在留空，等于改动前的
那份请求体一字不差。

`pytest` **284 passed / 6 skipped**（+10：温度留空/0/越界/读文件回落、发与不发各认一面、
存取与草稿与 GET 回 null）、`npm run build` 通过。8765 已用新代码重启。

# 重构记录

本文件按阶段记录 Niannian → Niannian2 重构的边界、决策与验证。
原项目 `Niannian/docs` 仅作架构理解材料，未经用户确认不作为约束。

## 阶段一：微信会话看板 + 只读接入（2026-10-14）

### 目标（用户定义）

搭好前端网页看板并接入微信，仅保留“微信会话”一页：能添加关注对话、
查看关注对话消息；与该阶段无关的功能按钮一律不做；非纯文本消息暂不格式化；
UI 与原版基本一致。

### 已确认的决策

1. 视觉参照 = 原版微信会话页（用户原话附图未送达，用户确认以原版为准）。
2. 关注会话后**自动导入**最近 N 条（默认 100），保留原版“历史上限+导入”
   按钮之外的最小闭环；不做手动导入按钮。
3. `.venv` 中指向失效旧路径的 `niannian 1.0.0` editable 残留已卸载。
4. `wechatauto-replica` 注册为 git submodule，锁定 1.2.5.1（fbfb026），
   与原项目一致；转换前逐文件哈希校验新旧副本一致。
5. 端口沿用 8765。

### 与原版的关键差异（本阶段有意为之）

- 关注语义收敛：原版“关闭监控仍继续采集”（因监控挂钩提炼调度）；阶段一
  没有提炼，故**取消关注即停止采集**，水位保留、重新关注续传不重复。
- 未搬运：媒体挂载/附件解析、身份映射与确认字段、实例锁、runs/model_calls
  诊断表、提炼/待办/画像/规则/设置/诊断各页。
- 前端组件全部本地手写（Button/Card/Input/Badge/Dialog），未引入
  shadcn/radix/clsx/tailwind-merge；配色沿用原版设计 token。
- 后端为全新最小实现：三张表（sessions/messages/checkpoints），
  借鉴原版“单线程串行读取 + 命令队列 + 水位同事务”的设计思路。

### 验证记录

- pytest：11 项通过（目录 upsert 保留关注态、去重、水位不回退、分页游标、
  发送者前缀/XML 根解析、is_self、去重键稳定性、无微信时明确报错）。
- 真机只读验证（本机登录微信）：连接成功，目录 89 个会话；关注群
  “26软工舍友の后花园”后自动导入 100 条真实消息；页面可见发送者昵称、
  时间、文本与 XML 原文（图片/转账/拍一拍未格式化，符合本阶段约定）；
  “加载更早消息”翻页正常；强制终止进程后重启，消息数与去重键保持
  100/100，水位续传未重复导入。
- UI 在内置浏览器实测：布局、状态条、弹窗关注流与原版一致度良好。

### 已知边界

- 目录中会出现系统会话（服务通知、brandsessionholder 等），本阶段不过滤。
- 消息正文长 XML 会占满气泡，属“暂不格式化”的约定表现。
- `catalog()` 在采集线程存活时同步读上游，超时 90s；线程未运行时回退本地目录。
- 待清理：`Niannian2/.replica-backup-tmp`（子模块转换前的临时备份副本，
  内容已校验与上游一致；沙箱策略拦住了删除命令，已加入 .gitignore，请手动删除）。

### 下一阶段候选（未启动，需用户确认）

- 非纯文本消息格式化（图片/视频/文件/转账/引用等）。
- 系统/无意义会话目录过滤。
- 提炼链路与待办看板（原版 engine/prompts/llm 等能力的全新实现）。

## 修复：微信发送者名字解析错误（2026-10-14）

### 症状

群聊出现根本不是群成员的署名（“吴寒”16 条、“助班学长”1 条），私聊里自己发的
消息全部署上对方名字（王五月会话 100 条只有 5 条 `is_self=1`）。原版没这个表现。

### 根因

微信 4.x 消息分片库中 `Msg_*.real_sender_id` 是**该分片库自身 `Name2Id` 表的
rowid**，id 空间按分片各自编号；上游 `wechatauto.db._sender_id_index()` 却用
`message_resource.db` 的全局 `SenderName2Id` 去解析（全库没有任何一处用到正确的
分片 `Name2Id`），于是 `get_messages` 给出的 `sender_username` 是**另一个人的
wxid**——实测本群 `real_sender_id=5` 分片内是“我自己”，全局表解析成“吴寒”。

正文带 `wxid_x:` 前缀的行（群聊普通文本）被 `split_sender` 的前缀救回，所以看着
是对的；**没有前缀的行全部落到错误映射**：自己发的文本、emoji、图片、系统消息。
私聊完全没有群前缀，故 `is_self` 恒为 0、自己的话全成对方说的。

原项目有同一处缺陷（同版本子模块、同样的 `origin or sender_username` 优先级），
只是它只导入过“全员带前缀”的通知群（180 条 `is_self` 全为 0），症状未暴露。

### 改动

只在 `niannian/wechat.py`，**不动子模块**（子模块是 detached HEAD 的第三方锁定）：

1. 新增 `sender_alias_map(conn, table, wanted)`：在指定分片内按
   `(sort_seq, local_id)` 联合 `Name2Id` 还原真实发送者 wxid。
2. `IsolatedDB` 新增 `_fix_senders()`，并覆写 `get_messages` / `get_new_messages`
   套用之；分片解析不到的行把 `sender_username` 置空，避免沿用上游错值。
3. `normalize_message` 的发送者优先级由「正文前缀优先」改为
   「**分片解析优先、正文前缀兜底**」。

### 验证

- pytest 14 项通过（新增 3 项：分片 id 空间隔离、系统消息空名、自身 rowid 不被
  全局表串号 + 前缀与分片冲突时以分片为准）。
- 真机清库重采：群 100 条署名全部落在该群 4 名真实成员内，原 16 条“吴寒”→“我”；
  私聊 `is_self` 由 95/5 变为分布自然的 56/44；89 条带前缀的行前缀与分片解析零冲突。
- 增量轮询走同一 `_fix_senders`，单独取 `get_new_messages` 逐条断言发送者是群成员。
- 浏览器实测群聊与私聊署名、气泡归属均正确。

### 残留

拍一拍 appmsg 的 `real_sender_id=9` 在 `Name2Id` 中 `user_name` 为空，回落显示
“群成员”（原版同场景错显示为“助班学长”）；空名系统类消息的署名策略待用户定。


## 阶段二：图片显示（2026-10-14）

### 目标（用户定义）

让图片能显示出来；库里**只落图片本地链接**；清库重新采集。用户另外指出：
原版对"没在微信里手动点开过的图片"处理有问题——那些其实有预览图文件、
能被解析出来，但原版没做。

### 实测到的三条事实

1. **磁盘文件名哈希只在 `packed_info_data` 里**。正文 XML 的 `md5` 属性是另一套
   值：实测 `md5="6793b97e…"` 那条图，磁盘文件叫
   `3d11d910dfa03787d8b96a2964079fd2_t.dat`。按 XML 的 md5 去 attach 目录找，
   23 条一条都找不到。
2. **未点开过的图片只有 `_t.dat` 预览图，且能解出来**（单字节 XOR，从文件尾
   `FF D9` 反推密钥，不需要图片 AES 密钥）。实测两个会话 23 张图：
   原图 9 / 本机下发那份 6 / **只有预览图 8**。上游 `download_image(tier='best')`
   本来就会回落到预览图档，所以"能不能解"不是问题，问题在**什么时候去解**。
3. 原版把提取只挂在采集那一刻（`MediaCache.enrich` 在 `_store` 里调用一次），
   而微信的预览图是**翻到那条记录才落盘**的。它自己的库里就有证据：
   `45948752706@chatroom` 28 条图片只有 8 条留下 `local_file`，而今天对这 32 条
   重跑 `tier='best'` 是 **32/32 全部可解**——文件一直在盘上、能解析，库里却没链接。

### 改动

新增 `niannian/media.py`（全新实现，未搬运原版 `media.py`）：

- `hash_from_blob` / `media_hash_map`：按 `(sort_seq, local_id)` 从
  `packed_info_data` 批量取本机文件哈希（上游 `get_messages` 不返回该列）。
- `parse_image` / `summarize`：识别 `<img>` 附件，入库正文换成 `[图片]`
  （尺寸留在 metadata，不进摘要——`cdnthumb*` 是预览图尺寸，标出来会误导）。
- `pick_tier`：原图 > 本机下发 > 预览图；`_h.dat` 小于 1KB 视为下载中断空壳。
- `ImageStore.attach`：解密落到 `data/wechat/media/<账号指纹>/`，
  文件名 `<会话>_<sort_seq>[_档位].<ext>`，只回传相对链接。
- `safe_media_path`：链接最多两段、拒绝对称路径/盘符/UNC/`..`。
- `wechat.py`：抽出 `_each_shard` 共用分片遍历；`_attach_media` 在采集线程内
  补 `media_md5` + `local_file`；`IsolatedDB.media_hashes` 走同一条只读通道。
- `api.py`：`GET /media/{name}` 托管本机图片；`_link_media` 在**读取时**凭
  `media_md5` 再补一次链接并回写库——只碰文件系统与工程缓存，不需要采集线程。
- `web/`：`mediaUrl()` 拼链接；`message.tsx` 渲染缩略图 + 点击放大 Dialog，
  弹窗标注档位（原图/本机图/预览图）；无文件时显示"本机暂无该图片文件"。

### 验证

- pytest 22 项通过（新增 8 项：图片 XML 识别与拒绝、`packed_info` 哈希提取、
  档位优先级与空壳降级、`safe_media_path` 八种越界、`ImageStore.attach` 落盘
  位置与链接形状、账号目录指纹）。
- `tsc -b` 无错、`npm run build` 通过。
- 真机清库重采：200 条消息、23 条图片**全部**拿到本机链接（原图 9/本机图 6/
  预览图 8）；`GET /media/<预览图>` 返回 200 `image/jpeg`（`FF D8 FF`，118x210），
  原图返回 200 `image/png`。
- 越界探测 `../niannian.db`、`%2e%2e%2fconfig.json`、`C:/Windows/win.ini`、
  `/etc/passwd`、三段穿越路径全部 404。
- 回填路径实测：抹掉一条的 `local_file` 后再请求该页，链接自动补回并持久化。
- 浏览器实测：群会话 9 个图片气泡 8 个渲染出图，抹掉哈希的那条正确显示
  "本机暂无该图片文件"空态；放大弹窗 Esc 与遮罩点击均能关闭，档位标注正确。
  （内置浏览器标签处于 hidden 状态时 Chrome 不加载 `loading="lazy"` 图片，
  验证时改为 eager 后 9/9 全部加载；截图能力受限于该隐藏面，未取到视觉截图。）

### 已知边界

- 只处理图片；视频/语音/文件/卡片/拍一拍仍入库原始 XML。
- 预览图是低分辨率档，放大后仍模糊——已在弹窗标注"预览图"，不假装是原图。
  要真原图必须让微信去下载，那属于驱动界面，超出只读边界。
- 回填只认采集时已写入的 `media_md5`；早于本版本入库、没有该字段的老行不会补
  （本轮已清库重采，当前库内不存在这种行）。
